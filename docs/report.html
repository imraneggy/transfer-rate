1. Executive summary

Exchangia is an open-source Android 14+ app that compares AED → INR remittance rates across ten verified UAE providers in near real time, alongside a mid-market reference benchmark and a UAE-vs-India gold rate module. The data pipeline runs as a free unattended GitHub Actions cron, publishes a single static JSON to GitHub Pages, and the app fetches that file directly — no backend, no analytics, no account, no cloud sync.

2. The product

What it does

A single screen shows the current AED → INR mid-market rate, the live UAE-vs-India gold rate, and a sortable list of providers with how much each pays out per AED. The largest payer gets a BEST badge. Tap a provider card → a 10-day rate-history sheet opens in-app (no browser redirect). Tap the gold module → a 30-day gold history sheet with 1g and 8g, 24K and 22K, side by side.

What it explicitly is not

  • Not a remittance broker — we don't transfer money or take a cut.
  • Not a social or notification app — there are zero background pings.
  • Not a financial advisor — the disclaimer in About is real; rates shown are indicative only.
  • Not affiliated with any of the listed providers. Provider names and logos are trademarks of their respective owners, used for nominative identification in a comparison context.

3. System architecture

┌──────────────────────────────┐ │ GitHub Actions (free tier) │ │ cron every ~hour │ └──────────────┬───────────────┘ │ ▼ ┌──────────────────────────────┐ │ scrapers/run_all.py │ ── fetches 11 sources in parallel │ (Python 3.12 + httpx) │ with hard timeouts, retries, └──────────────┬───────────────┘ stale-tolerance fallback │ ▼ ┌──────────────────────────────┐ │ public/rates.json │ ── atomic write, schema v2 │ public/history.json │ ── rolling 10-day per-provider │ public/gold_history.json │ └──────────────┬───────────────┘ │ git commit + push ▼ ┌──────────────────────────────┐ optional residential runner │ GitHub Pages │ ◄──── injects LuLu via │ imraneggy.github.io/ │ scrapers/lulu_inject.py │ transfer-rate/rates.json │ └──────────────┬───────────────┘ │ HTTPS GET (network-security-config locked to host) ▼ ┌──────────────────────────────┐ │ Android app (Compose) │ ── stale-while-revalidate cache, │ com.transferrate.app │ pull-to-refresh, dark/light/auto └──────────────────────────────┘

Why this shape

  • No backend → nothing to operate, monitor, or pay for; no PII storage liability; no scaling work.
  • Static JSON on Pages → the app reads a single URL hosted on a domain it explicitly trusts via Network Security Config. CDN caching is free and global.
  • Scraping in CI not in-app → the app makes one network call per refresh. No third-party domain pings, no analytics SDKs, no certificate-pinning fragility.

Per-call hardening

  • Hard per-call timeout: 25 seconds.
  • Polite User-Agent (transfer-rate-bot/1.0) with maintainer contact, plus browser-style UA fallback for CDN-protected sites (Federal Exchange).
  • Retry-with-backoff for transient failures (get_with_retry): 3 attempts at 0.5s/1s gaps.
  • Stale tolerance: when a fresh fetch errors, the orchestrator preserves the last good quote and marks it status=stale so the app never shows an empty cell for a previously-known-good provider.
  • Validation guard rails: rates outside [0.0001, 10000] are rejected as parse bugs, not forwarded.

5. Gold rate module

Sits 50/50 with the mid-market header on the home screen. Two independent sources fetched in parallel:

SideSourcePattern
UAE Khaleej Times HTML table cells: <td>24K</td><td>556.00</td>
India BankBazaar Inline JSON: {"date":"...","prices":{"22K_1G":13935,"24K_1G":14632}} — full 30-day series

India history comes for free from BankBazaar's inline series (30+ days). UAE history is accumulated locally into data/uae_gold_history.json — Khaleej Times only publishes today's reading, so the orchestrator appends each scrape's rate and prunes to the most recent 30 days.

Tap the gold module → sheet shows snapshot grid (1g + 8g for both carats for both countries), 24K trend sparklines side by side, and a unified daily history table.

  • Top-level permissions: {} denies everything by default; job-scoped grants only contents: write / pages: write / id-token: write as needed.
  • Third-party actions pinned by full commit SHA, not tag.
  • concurrency.cancel-in-progress: true prevents racing runs.
  • Optional release-signing keystore via repo secrets (KEYSTORE_BASE64, KEYSTORE_PASSWORD, KEY_ALIAS, KEY_PASSWORD); falls back to debug signing for sideload-only builds.

9. The LuLu story

LuLu Exchange has been the only consistently-blocked provider. The journey, in chronological order, illustrates why "just write a scraper" turned out to be 4 different attempts:

Attempt 1 — Direct port-9443 fetch

LuLu's rate API runs on https://lieservices.luluone.com:9443/liveccyrates with a Gravitee key embedded in their public homepage JS. Works perfectly on residential IPs. Fails in CI: GitHub Actions runners block all outbound traffic to non-standard ports. CI: blocked

Attempt 2 — Cloudflare Worker proxy

Wrote a 100-line Worker to forward port-9443 calls. Discovered Cloudflare Workers also restrict fetch() to ports 80/443 — same wall, different name. Worker: 502 immediately

Attempt 3 — Cloudflare Worker via LuLu's port-443 fallback

Found a second LuLu API at orville.luluone.com (port 443) that powers their rate-history graph. Public OAuth-style credentials embedded in homepage JS. Auth call works from CF; rate-history POST is WAF-blocked from Cloudflare's IP ranges (520 errors). Worker: 520 from upstream

Attempt 4 — Headless Chromium in CI (Playwright)

Loaded LuLu's homepage in a real browser inside CI. The page rendered, but its in-page JS made the same blocked port-9443 call — the rate placeholder never updated and wait_for_function timed out. The browser was just a UI for the same blocked HTTP call. Playwright: timeout

Attempt 5 — Self-hosted runner on residential IP working

The only path that actually works. Pipeline shipped in v0.13.6:

  • scrapers/lulu_inject.py — fetches LuLu via the working direct API and injects into public/rates.json at index 5 (idempotent; re-runs are safe).
  • .github/workflows/scrape-lulu-residential.yml — cron every 30 min, runs-on: [self-hosted, lulu-residential]. Push-retry loop handles concurrent commits from scrape.yml.
  • infra/lulu-residential/README.md — 5-step setup guide for installing the runner on home box, Pi, or residential VPS.

Until the user installs the residential runner, _build_providers omits LuLu so the app shows no error card. The moment the runner comes online, the next 30-min tick injects LuLu cleanly.

Lesson: when the bottleneck is L3/L4 firewall, you need a different network path, not a different user agent. Useful litmus test: would curl --resolve or socks5:// flags help? If yes, the browser is overkill; if no, the browser won't either.

Could be added with paid infrastructure

PathAddsCost

Yield curve: the first 10 providers were findable in minutes each (public APIs, WP plugins exposing rates inline, marquee tags). Provider 11 onwards costs 10–100× more per add because the easy patterns are exhausted — you start needing session cookies, headless browsers, residential proxies, or proxy infrastructure. The S-curve flattens hard around the 10–15 mark for any scraping project; this is normal.

11. Security & privacy

App-side

  • One permission: android.permission.INTERNET. Nothing else — no location, no contacts, no storage beyond app-private SharedPreferences.
  • Network Security Config restricts cleartext to nothing and HTTPS to a single host (imraneggy.github.io).
  • No analytics, no telemetry, no advertising, no account, no cloud sync.
  • R8 minification + resource shrinking on release builds; isDebuggable = false.
  • Backup rules exclude any per-user state from Google Auto-Backup.

Pipeline-side

  • No secrets stored in CI for the FX scrape; data is public.
  • Scrape commits are signed by a dedicated bot identity (transfer-rate-bot) so commit history shows a clean separation between human and machine commits.
  • Polite scraping: identifying User-Agent, single concurrent connection per provider host, hard timeout, no aggressive retry storms.
  • git.txt (the maintainer PAT) is in .gitignore and never reaches CI.

Disclosed in the app

The About screen carries the trademark/nominative-use disclaimer plus the standard "indicative rates, confirm at provider, not financial advice" block. DISCLAIMER.md, PRIVACY.md, and SECURITY.md are all at repo root.

12. Roadmap

Concrete next adds (already-built, pending user action)

  • Install the residential runner per infra/lulu-residential/README.md → LuLu re-appears in the rates list within 30 min.

Possible expansions

  • Multi-currency corridors (PKR, PHP, BDT, EGP, NPR, LKR) — scrapers and schema already accept these; only INR is enabled in SUPPORTED_TARGETS today. Re-enabling per corridor is a one-line change once each provider's per-corridor parser is written.
  • Promotional / first-transfer rate surfacing across more providers — only Remitly currently exposes a structured promo rate; other providers would require per-provider scraper extensions.
  • Notification on rate threshold ("alert me when AED→INR > 25.85") — would require either device-local scheduling (FREE, slightly stale) or a backend (unwanted).
  • F-Droid submission once a release-signing keystore is configured — fastlane metadata is already in place at fastlane/metadata/android/en-US/.

Explicitly out of scope

  • iOS port — Android-only is intentional given the maintainer's constraints.
  • Account-required providers — would compromise the privacy stance.
  • Backend / serverless functions — would violate the "no operational cost, no PII" constraint.

1. Executive summary

Exchangia is an open-source Android 14+ app that compares AED → INR remittance rates across eleven verified UAE providers in near real time, alongside a mid-market reference benchmark, a UAE-vs-India gold rate module, and a Mosque Finder using OpenStreetMap data. The data pipeline runs as a free unattended GitHub Actions cron, publishes a single static JSON to GitHub Pages, and the app fetches that file directly — no backend, no analytics, no account, no cloud sync.

2. The product

What it does

A single screen shows the current AED → INR mid-market rate, the live UAE-vs-India gold rate, and a sortable list of providers with how much each pays out per AED. The largest payer gets a BEST badge. Tap a provider card → a 10-day rate-history sheet opens in-app (no browser redirect). Tap the gold module → a 30-day gold history sheet with 1g and 8g, 24K and 22K, side by side.

What it explicitly is not

  • Not a remittance broker — we don't transfer money or take a cut.
  • Not a social or notification app — there are zero background pings.
  • Not a financial advisor — the disclaimer in About is real; rates shown are indicative only.
  • Not affiliated with any of the listed providers. Provider names and logos are trademarks of their respective owners, used for nominative identification in a comparison context.

3. System architecture

┌──────────────────────────────┐ │ GitHub Actions (free tier) │ │ cron every ~hour │ └──────────────┬───────────────┘ │ ▼ ┌──────────────────────────────┐ │ scrapers/run_all.py │ ── fetches 11 sources in parallel │ (Python 3.12 + httpx) │ with hard timeouts, retries, └──────────────┬───────────────┘ stale-tolerance fallback │ ▼ ┌──────────────────────────────┐ │ public/rates.json │ ── atomic write, schema v2 │ public/history.json │ ── rolling 10-day per-provider │ public/gold_history.json │ └──────────────┬───────────────┘ │ git commit + push ▼ ┌──────────────────────────────┐ optional residential runner │ GitHub Pages │ ◄──── injects LuLu via │ imraneggy.github.io/ │ scrapers/lulu_inject.py │ transfer-rate/rates.json │ └──────────────┬───────────────┘ │ HTTPS GET (network-security-config locked to host) ▼ ┌──────────────────────────────┐ │ Android app (Compose) │ ── stale-while-revalidate cache, │ com.transferrate.app │ pull-to-refresh, dark/light/auto └──────────────────────────────┘

Why this shape

  • No backend → nothing to operate, monitor, or pay for; no PII storage liability; no scaling work.
  • Static JSON on Pages → the app reads a single URL hosted on a domain it explicitly trusts via Network Security Config. CDN caching is free and global.
  • Scraping in CI not in-app → the app makes one network call per refresh. No third-party domain pings, no analytics SDKs, no certificate-pinning fragility.

Per-call hardening

  • Hard per-call timeout: 25 seconds.
  • Polite User-Agent (transfer-rate-bot/1.0) with maintainer contact, plus browser-style UA fallback for CDN-protected sites (Federal Exchange).
  • Retry-with-backoff for transient failures (get_with_retry): 3 attempts at 0.5s/1s gaps.
  • Stale tolerance: when a fresh fetch errors, the orchestrator preserves the last good quote and marks it status=stale so the app never shows an empty cell for a previously-known-good provider.
  • Validation guard rails: rates outside [0.0001, 10000] are rejected as parse bugs, not forwarded.

5. Gold rate module

Sits 50/50 with the mid-market header on the home screen. Two independent sources fetched in parallel:

SideSourcePattern
UAE Khaleej Times HTML table cells: <td>24K</td><td>556.00</td>
India BankBazaar Inline JSON: {"date":"...","prices":{"22K_1G":13935,"24K_1G":14632}} — full 30-day series

India history comes for free from BankBazaar's inline series (30+ days). UAE history is accumulated locally into data/uae_gold_history.json — Khaleej Times only publishes today's reading, so the orchestrator appends each scrape's rate and prunes to the most recent 30 days.

Tap the gold module → sheet shows snapshot grid (1g + 8g for both carats for both countries), 24K trend sparklines side by side, and a unified daily history table.

9. The LuLu story

LuLu Exchange has been the only consistently-blocked provider. The journey, in chronological order, illustrates why "just write a scraper" turned out to be 4 different attempts:

Attempt 1 — Direct port-9443 fetch

LuLu's rate API runs on https://lieservices.luluone.com:9443/liveccyrates with a Gravitee key embedded in their public homepage JS. Works perfectly on residential IPs. Fails in CI: GitHub Actions runners block all outbound traffic to non-standard ports. CI: blocked

Attempt 2 — Cloudflare Worker proxy

Wrote a 100-line Worker to forward port-9443 calls. Discovered Cloudflare Workers also restrict fetch() to ports 80/443 — same wall, different name. Worker: 502 immediately

Attempt 3 — Cloudflare Worker via LuLu's port-443 fallback

Found a second LuLu API at orville.luluone.com (port 443) that powers their rate-history graph. Public OAuth-style credentials embedded in homepage JS. Auth call works from CF; rate-history POST is WAF-blocked from Cloudflare's IP ranges (520 errors). Worker: 520 from upstream

Attempt 4 — Headless Chromium in CI (Playwright)

Loaded LuLu's homepage in a real browser inside CI. The page rendered, but its in-page JS made the same blocked port-9443 call — the rate placeholder never updated and wait_for_function timed out. The browser was just a UI for the same blocked HTTP call. Playwright: timeout

Attempt 5 — Self-hosted runner on residential IP working

The only path that actually works. Pipeline shipped in v0.13.6:

  • scrapers/lulu_inject.py — fetches LuLu via the working direct API and injects into public/rates.json at index 5 (idempotent; re-runs are safe).
  • .github/workflows/scrape-lulu-residential.yml — cron every 30 min, runs-on: [self-hosted, lulu-residential]. Push-retry loop handles concurrent commits from scrape.yml.
  • infra/lulu-residential/README.md — 5-step setup guide for installing the runner on home box, Pi, or residential VPS.

Until the user installs the residential runner, _build_providers omits LuLu so the app shows no error card. The moment the runner comes online, the next 30-min tick injects LuLu cleanly.

Lesson: when the bottleneck is L3/L4 firewall, you need a different network path, not a different user agent. Useful litmus test: would curl --resolve or socks5:// flags help? If yes, the browser is overkill; if no, the browser won't either.

Across this and earlier sessions, 50+ UAE remittance providers + 20 banks have been probed. Below is the definitive enumeration of the practical ceiling:

Could be added with paid infrastructure

PathAddsCost
Self-hosted residential runner (already shipped, ready to install) LuLu (1 provider) $0 (your hardware) to ~$5/mo (residential VPS)

Yield curve: the first 10 providers were findable in minutes each (public APIs, WP plugins exposing rates inline, marquee tags). Provider 11 onwards costs 10–100× more per add because the easy patterns are exhausted — you start needing session cookies, headless browsers, residential proxies, or proxy infrastructure. The S-curve flattens hard around the 10–15 mark for any scraping project; this is normal.

11. Security & privacy

App-side

  • Permissions (full list, post v0.15.0):
    • android.permission.INTERNET — rates JSON + OSM tiles + Overpass mosque queries.
    • android.permission.ACCESS_NETWORK_STATE — offline detection.
    • android.permission.ACCESS_FINE_LOCATION / ACCESS_COARSE_LOCATION — Mosque Finder only, foreground only. Never requested in background. The coordinate is used to centre the map and to sort mosques by walking distance; it is never sent off-device (the Overpass query takes a radius and returns mosques near a point, but uses our own lat/lon parameters — no telemetry endpoint receives the device's position).
  • Still no contacts, no SMS, no camera, no microphone, no storage beyond app-private SharedPreferences.
  • Network Security Config restricts cleartext to nothing; HTTPS allowed for the rates host (imraneggy.github.io), the OSM tile host (tile.openstreetmap.org), and the Overpass host (overpass-api.de).
  • No analytics, no telemetry, no advertising, no account, no cloud sync.
  • No Google Play Services dependency — location uses Android LocationManager directly; map uses MapLibre Native (open source). App works on F-Droid / GrapheneOS / Huawei.
  • R8 minification + resource shrinking on release builds; isDebuggable = false.
  • Backup rules exclude any per-user state from Google Auto-Backup.

Pipeline-side

  • No secrets stored in CI for the FX scrape; data is public.
  • Scrape commits are signed by a dedicated bot identity (transfer-rate-bot) so commit history shows a clean separation between human and machine commits.
  • Polite scraping: identifying User-Agent, single concurrent connection per provider host, hard timeout, no aggressive retry storms.
  • git.txt (the maintainer PAT) is in .gitignore and never reaches CI.

Disclosed in the app

The About screen carries the trademark/nominative-use disclaimer plus the standard "indicative rates, confirm at provider, not financial advice" block. DISCLAIMER.md, PRIVACY.md, and SECURITY.md are all at repo root.

12. Roadmap

Already shipped since v0.13.6

  • v0.14.0 — gold popup gained 22K trend sparklines, 30-day High/Low/Avg pills per region, and a 24K | 22K carat selector. Mid-market header is now tappable and opens a 30-day history sheet. Typography pass: tabular figures baked into title styles; bolder labels; WCAG contrast bumps on outline + onSurfaceVariant.
  • v0.15.0 — Mosque Finder shipped (OSM tiles via osmdroid, mosque data via Overpass API, distance-sorted list, Android LocationManager for fix). Lari Exchange added as the 12th rate provider.
  • v0.16.0 — map renderer migrated from osmdroid to MapLibre Native 11.11 for smooth pinch-zoom + rotation. Lari Exchange brand logo bundled. Location code modernised to getCurrentLocation (was deprecated requestSingleUpdate); no more silent Dubai fallback — specific failure modes get specific error messages.
  • v0.16.1 — UX honesty: removed Dubai sample placeholder, added a refresh icon (↻) in the Mosque Finder top app bar so users can re-fetch after toggling location services on/off.
  • v0.16.2 — you-are-here marker on the map; walking distance baked into each mosque pin (350 m, 1.2 km) so users see distances at a glance.
  • v0.16.3 — refreshed app launcher icon (Stair-Step E on teal gradient with gold accent dot); foreground PNG now rendered at all 5 DPI buckets.

Concrete next adds (already-built, pending user action)

  • Install the residential runner per infra/lulu-residential/README.md → LuLu re-appears in the rates list within 30 min.

Possible expansions

  • Vector tiles in the Mosque Finder — one-string change in MapLibreMapView.kt's OSM_RASTER_STYLE constant. Free options: MapTiler free tier (100K loads/mo, requires API key), Versatiles community vector tiles (no key), or self-hosted PMTiles via Cloudflare R2 (ultimate $0).
  • Multi-currency corridors (PKR, PHP, BDT, EGP, NPR, LKR) — scrapers and schema already accept these; only INR is enabled in SUPPORTED_TARGETS today. Re-enabling per corridor is a one-line change once each provider's per-corridor parser is written.
  • Aladhan prayer-times overlay in the Mosque Finder — pairs naturally with mosque markers; Aladhan API is free, returns prayer times for any (lat, lon, date).
  • Promotional / first-transfer rate surfacing across more providers — only Remitly currently exposes a structured promo rate; other providers would require per-provider scraper extensions.
  • Notification on rate threshold ("alert me when AED→INR > 25.85") — would require either device-local scheduling (FREE, slightly stale) or a backend (unwanted).
  • F-Droid submission once a release-signing keystore is configured — fastlane metadata is already in place at fastlane/metadata/android/en-US/.

Explicitly out of scope

  • iOS port — Android-only is intentional given the maintainer's constraints.
  • Account-required providers — would compromise the privacy stance.
  • Backend / serverless functions — would violate the "no operational cost, no PII" constraint.

14. Step-by-step implementation guide

Complete recipe from clone to a running APK on your phone. Tested on Windows, macOS, and Ubuntu.

14.1 Clone the repository

git clone https://github.com/imraneggy/transfer-rate.git
cd transfer-rate

14.2 Set up the Python scraper environment

python -m venv .venv
# Windows:
.venv\Scripts\activate
# macOS / Linux:
source .venv/bin/activate

pip install -r requirements.txt

14.3 Run the scrapers locally

# Run all 11 sources in parallel and write public/rates.json
python -m scrapers.run_all --out public/rates.json

# Run pytest to verify nothing has drifted
python -m pytest tests/test_scrapers.py -v

14.4 Set up the Android build environment

You need:

  • Android Studio Ladybug (2024.2.1) or newer
  • JDK 17 (bundled with recent Android Studio versions)
  • Android SDK 35 + Build Tools 35.0.0

Open android/ in Android Studio. The Gradle wrapper auto-downloads the pinned 8.11.1 distribution (SHA256-verified).

14.5 Build a debug APK

cd android
./gradlew assembleDebug
# APK lands at:
# app/build/outputs/apk/debug/app-debug.apk

14.6 Build a release APK (signed)

A. Local release build

# Generate a 25-year keystore once
keytool -genkey -v -keystore release.jks -keyalg RSA -keysize 4096 \
  -validity 9125 -alias exchangia

# Create android/keystore.properties (gitignored):
storeFile=../../release.jks
storePassword=YOUR_PASSWORD
keyAlias=exchangia
keyPassword=YOUR_PASSWORD

# Build:
./gradlew assembleRelease

B. CI release build (free, automated)

git tag -a v0.14.0 -m "v0.14.0 release notes"
git push origin v0.14.0
# android-build.yml builds 4 APKs and creates a GitHub Release

For Play Store-acceptable signing in CI, add 4 repo secrets: KEYSTORE_BASE64 (base64 of release.jks), KEYSTORE_PASSWORD, KEY_ALIAS, KEY_PASSWORD. Without these, the workflow falls back to debug-signing automatically.

14.7 Set up the GitHub Pages publish flow

One-time:

  1. Repo → Settings → Pages
  2. Source: GitHub Actions

The scrape.yml workflow already deploys public/ on every successful run.

14.8 Optional: residential runner for LuLu

See infra/lulu-residential/README.md — 5-step guide. Adds LuLu to the rates list.

14.9 Verify the full pipeline end-to-end

  1. Trigger a scrape: https://github.com/imraneggy/transfer-rate/actions/workflows/scrape.yml → Run workflow.
  2. ~90 seconds later, check https://imraneggy.github.io/transfer-rate/rates.json — the completed_at timestamp should be fresh.
  3. Open the app, pull-to-refresh.

Reporting a vulnerability

Please do not open a public GitHub issue for security problems.

Email the maintainer instead. Include:

  • A description of the issue
  • Steps to reproduce
  • Affected commit / app version
  • Your contact info if you'd like a credit

You can expect:

  • Acknowledgement within 72 hours
  • Fix or mitigation plan within 14 days for confirmed issues
  • Public disclosure coordinated with you

What counts as a vulnerability for this project

  • Anything that lets a third party feed a malicious rates.json into the app pipeline (e.g. compromise of the GitHub Actions workflow)
  • Code execution paths in the app from untrusted JSON input
  • Bypass of the network security allowlist
  • Leakage of any user data (note: the app intentionally collects none — if you find it does, that itself is the vulnerability)

Hardening choices already in place

  • GitHub Actions workflows pin third-party actions by full commit SHA.
  • permissions: {} at workflow root denies everything by default; only the commit step receives contents: write.
  • Android Network Security Config restricts connections to imraneggy.github.io. No cleartext.
  • usesCleartextTraffic="false" on the <application> element.
  • allowBackup="false" and explicit data_extraction_rules.xml.
  • App requests only INTERNET.
  • JSON parser configured strictly (isLenient=false); document is bound-checked before being rendered.
  • R8 full-mode strips debug-level Log calls in release builds.

Out of scope

  • Vulnerabilities in third-party provider websites we scrape (report those to the provider directly).
  • Network-level attacks against the user's device that are not specific to this app.

Takedown / removal request

If you represent a remittance provider listed in this project and you would like your service removed, here is the process. We respect such requests and act within 24 hours.

How to request

Open a GitHub issue titled Takedown request: <provider>, or email the maintainer directly. Include:

  1. Your name and role at the provider
  2. Confirmation that you are authorised to make this request
  3. The exact provider entry to remove (or modify)
  4. Any supporting context (e.g. ToS section, brand-protection concern)

We do not require a formal legal notice. A clear request from a verifiable provider contact is enough to start removal.

What "removal" means

  • The provider is removed from scrapers/run_all.py so it stops being scraped.
  • The provider is removed from public/rates.json on the next run.
  • Historical commits remain in git history, but no current build references the provider.
  • The Android app, which fetches the live JSON, stops showing the provider as soon as users open the app and the JSON refreshes.

Modification, rather than removal

If you'd like the listing to exist but display differently — corrected name, official deep link to your product, brand styling — open a regular issue and we'll happily collaborate.

Brand and trademarks

Provider names are used nominatively to identify the source of the rate. We do not use provider logos, registered marks, or other branded assets in the app. If we have inadvertently included any, please flag it and we will remove immediately.

16.7 Contributing guide

CONTRIBUTING.md — canonical source.

Contributing

Thanks for considering a contribution. The most common change is adding or fixing a provider scraper. This guide walks through that.

Ground rules

  1. Public data only. Do not authenticate, do not replay private mobile APIs, do not bypass paywalls or rate limits.
  2. Conservative parsing. A scraper that surfaces a wrong number is worse than one that surfaces no number. Prefer raising an error to guessing.
  3. Polite traffic. One request per scrape; identify yourself via the shared User-Agent in scrapers/utils.py.
  4. No new dependencies in requirements.txt without discussion. Each added dependency is a supply-chain liability.
  5. All PRs include a brief test note — paste the local output of python -m scrapers.<your_scraper> on a recent run.

Adding a provider scraper

  1. Create scrapers/<provider>.py. Use scrapers/wise.py as a template: - id (slug, lowercase) and display_name - fetch_inr(amount_aed) returns a Quote
  2. Import and register it in scrapers/run_all.py (PROVIDERS list).
  3. Run locally: bash python -m scrapers.run_all cat public/rates.json
  4. Confirm your provider's row has status="ok" and a sane rate.
  5. Open a PR against main. The CI workflow (scrape.yml) will exercise your scraper on the merge.

Allowed sources

  • Public web pages displaying rates (no login needed)
  • Public APIs documented for marketing/widget use
  • RSS/JSON feeds the provider publishes

Disallowed sources

  • Authenticated endpoints (even if you have an account)
  • Reverse-engineered mobile APIs that require captured tokens or apk- extracted secrets
  • Anything behind an explicit "Terms of Service" prohibiting scraping (read it before adding)

Reporting a bug or wrong rate

Open a GitHub issue with: * Provider name * What rate the app shows vs. what the provider's site shows * Time observed (UTC) * Screenshot of both, if possible

Wrong-rate issues are P0 — we patch and force a fresh scrape ASAP.

Code style

  • Python: 4-space indent, type hints, no print debugging in committed code
  • Kotlin: official style (already enforced via kotlin.code.style=official)
  • No comments that restate the code; comments explain why.

Disclosure

Found a security issue? See SECURITY.md. Do not file public issues for vulnerabilities.
